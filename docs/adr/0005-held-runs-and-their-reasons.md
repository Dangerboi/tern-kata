# A run whose outcome is uncertain is held, and the reason says what to check

A held run stops automatic execution and waits for the user, who resumes it or abandons it. The worker never repeats a prompt that may have reached the agent. Holds are only for uncertainty; an outcome the worker can prove is recorded as `succeeded` or `failed` instead.

herdr-kata (holds.md, run-lifecycle.md) has about thirty hold reasons. Most exist because Herdr runs a long-lived interactive agent in a pane that the worker can only observe. An omp process the worker spawned has one clear end: it exits, and the worker holds its status. Those reasons fall away; the rule behind them stays.

## Decisions

- **Rule: adopt.** A prompt possibly delivered is never sent again for that attempt. Recovery continues saved local execution; kata's run status never authorizes a new attempt.
- **Classes: adopt.** *Pre-admission* (no outcome; slot and overlap gate free; cannot resume): `admission_rejected`, `create_rejected`. *Uncertainty* (outcome `unknown` in kata; overlap gate held; slot held while a process may be alive): the reasons below.
- **Uncertainty reasons.** `secret_unavailable`: a `secret_refs` source could not be read, nothing was started (adopt). `launch_unproven`: the journal says a launch began and holds no start record, so the process may exist (adapt of herdr-kata's saved launch intent). `interrupted`: the worker was stopped or killed while a step ran (adapt of `command_outcome_unknown`). `no_receipt`: a process started and its group is gone but no exit status was recorded (adopt as `command_no_receipt`, for omp as well as commands). `group_unproven`: the process group is still present or cannot be checked (adopt as `command_group_unproven`). `invalid_prompt`: the expanded prompt exceeds 256 KiB or cannot be written (adopt). `execution_error`: the worker failed inside its own code; read the log (adopt).
- **Not holds.** A timeout kills the process group (SIGTERM, then SIGKILL after 10 s), proves it gone and records `failed` "timed out" (spec). herdr-kata holds `timeout` because it will not interrupt a working agent a person may be watching; no one is watching a headless run, and a stuck agent must not keep capacity. A spawn error (omp missing, checkout gone) and a nonzero exit with the group gone are certain: `failed`, with the cause in the summary.
- **Rejected reasons.** `timeout`, `prompt_budget`: static check at admission instead (ADR-0008). `no_result`, `no_activity`, `agent_lost`, `launch_timeout`, `pane_busy`, `agent_unproven`, `submission_unproven`, `recovery_unproven`, `agent_switch_unproven`, `herdr_env_unclean`, `agent_start_failed`: all concern Herdr occupant, pane, readiness or environment proof, or a report file omp does not write. `invalid_note`, `step_failed`, `loop_pending`, `loop_exhausted`, `loop_stuck`: notes, park and maker/checker loops are rejected (ADR-0008).
- **Quota and login holds (`agent_quota`, `agent_login`): conditional adopt.** herdr-kata reads Codex and Claude session files to tell a usage limit from a failure, so retries and loops are not burned and the user resumes after the reset. omp's JSON output has no verified error kind yet. The first worker ticket checks it; if omp reports a structured rate-limit or auth error, those two holds are added with the same rules (no retry consumed, explicit resume only). Until then a failed run's summary carries omp's last error text.
- **Resume: adapt.** The Runs page `u` and the control socket accept a resume only for an uncertainty hold, with an intact journal belonging to this executor, every recorded process group proven gone (the worker never kills a process to make resume possible), the Project's lease held, and the Issue still open. Pre-admission holds refuse resume. Acceptance durably consumes the request uid and records the generation, the new attempt, the slot reservation and one fresh expiry from the timeout frozen at admission, before anything starts. A running observation keeps the original start time and clears the end. herdr-kata resumes by sending a new prompt that warns of partial work; the spec resumes with `omp --restore <session>`, which continues the interrupted turn without a prompt. If the session file does not exist (a `launch_unproven` crash before omp wrote one) resume is refused and only abandon remains. A held command step reruns its command.
- **Abandon: adapt.** `A` records `cancelled` with "abandoned by <actor>" and the held reason, frees the slot and overlap gate once the groups are proven gone, and comments on the Issue. herdr-kata's `release` (hand off, outcome preserved or `unknown`) and `abandon` (record a lost journal) become one verb; kata gets `cancelled` when a journal exists and `unknown` "local state lost" when it does not (ADR-0002). Pre-admission holds abandon without writing to kata. Settled runs refuse.
- **Reporting a hold: adopt.** A held run is recorded in kata as `unknown` with the reason first in the summary, commented on a per-run Issue, and notified to the Issue's owner or author; kata's Inbox then shows it. The Runs page shows `held: <reason>`.

## Consequences

- A user who sees "held" always has a reason and, for resumable ones, a session to read first (`o` on the Runs page).
- No hold reason depends on a detail of omp's terminal UI; the set shrinks to what a process either did or did not do.
