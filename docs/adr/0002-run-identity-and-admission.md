# A run's identity is derived; an observation is its admission fence

A Run's uid is a ULID built from the occurrence time and a hash of the Cron job and the occurrence, so a rebuilt schedule finds the same Run. The worker launches nothing until a revision-0 `running` observation for that uid has been accepted by kata. Existing evidence in kata vetoes a launch; local state loss never permits a replacement.

This follows herdr-kata (kata-adapter.md "Identity and admission", run-lifecycle.md), which solved it against real double-launch failures. kata's contract (cron.md, "Independent run evidence") supplies the primitives: an observation is created at revision 0, an identical retry replays, and a different immutable identity conflicts. It reserves no occurrence, so the worker must.

## Decisions

- **Uid: adopt.** `ULID(ms of the occurrence, first 10 bytes of SHA-256("tern-kata/run/v1\0" + job uid + "\0" + occurrence key))`. The occurrence key is the UTC RFC 3339 instant with nanoseconds, or `manual:<run uid>` for a run requested by `R` or `tern-kata run`. A manual uid is random once and kept; the worker saves the prepared journal before it answers the request on the control socket, so the caller sees the uid only after it is durable. herdr-kata's request files are not needed: the socket reply is the acknowledgement.
- **Veto: adopt.** Before preparing a uid with no local journal the worker reads `cron run show`. Evidence, or a quarantine entry, vetoes preparation. Only a `not_found` answer permits it; any other failure leaves the occurrence pending.
- **Order: adopt.** Prepare and save the journal (frozen definitions, definition event uids, input, checkout, profile, timeout, a random `journal_id`) first. Then resolve the per-run Issue. Then send the observation `{status: running, expected_revision: 0, summary: {version: 1, message: "admitted <journal_id>"}}`, identical on every retry. A created reply, or an exact replay from this journal, authorizes execution. A conflict is never read back as admission: the run is held `admission_rejected`, the slot and overlap gate are released, and any created Issue is left for the user. A `not_found` stays prepared and retries the same observation without executing.
- **Per-run Issue: adapt.** herdr-kata creates with a stable key and, on a look-alike conflict, reads back by a run marker or retries once with `--force-new`. kata's docs say an idempotency key wins over `--force-new` and that the look-alike check compares only title and body. So the worker always sends the key `tern-kata:<run uid>` together with `--force-new` and the marker `tern_kata.run=<run uid>`, and the readback path disappears. Per-run titles gain the UTC occurrence like herdr-kata's and kata's own children. A fatal create refusal holds `create_rejected` and is never retried automatically.
- **Existing-Issue policy: adopt.** The Issue must be open before execution; waiting for that takes no slot. The worker only comments on it and never closes, relabels or writes metadata. Notify jobs have no readiness requirement.
- **Lost journal: adopt.** A `running` observation of this executor with no local run directory is never rerun. `tern-kata worker doctor` lists them; `abandon` records `unknown` with the summary "local state lost" and comments on the Issue.
- **Author rule: reject.** herdr-kata schedules a job automatically only when the job's author equals the lane's actor, because several installations with different actors may share a Project there. Here trust is all or nothing per Project (spec) and one worker serves a Project (ADR-0003), so every enabled adapter job runs.
- **Native children and explicit issue requests: reject.** herdr-kata admits kata's recurring children and `herdr_kata.request` Issues through the inbox. The spec leaves native jobs to kata's daemon (story 77) and adds no request path. Skipping them removes the admission-receipt metadata, inbox scanner and acknowledgement rules. Native delivery creates no observation, so nothing is lost.
- **Run parent (`options.run_parent`): reject for now.** It groups per-run Issues under a parent. The spec's Issue policy has no such field and the Job card would need one. The create is where it would freeze, so adding it later changes nothing here.

## Consequences

- The observation fence is exact only on one authoritative daemon. Replicas that accept writes independently defeat it, as in herdr-kata; the worker serves the daemon it discovers (ADR-0001) and federation stays out of scope.
- Two workers sharing an executor label can admit the same run. The label must be unique and stable; ADR-0003 and ADR-0010 cover it.
