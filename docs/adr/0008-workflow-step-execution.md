# A workflow is one run whose steps execute serially, each in its own process

A workflow job is recorded as one Run. Its steps run one at a time in dependency order; a prompt step is one fresh `omp` process, a command step is one `sh -c` process, and each step is its own attempt with its own session and output. Failure and retry rules follow kata's workflow format and herdr-kata's reading of it. Extensions herdr-kata adds to that format are rejected.

Sources: herdr-kata definitions.md "Workflows", agent-contract.md "Command results", loops.md; kata cron.md "Workflow definitions".

## Decisions

- **Order: adopt.** Serial, topological, with definition order breaking ties. `after` naming a missing or later step, a duplicate key, `retries` outside 0 to 100, or a step with both or neither of `command` and `prompt` makes the workflow unsupported before admission. Kata checks these already; the Worker checks them again, with the rest of kata's definition rules, through the one validator the Workflows page also uses before it saves (`cronjob.ValidateWorkflow`, kata's order, the Workflow card's wording). The refusals below (`on_fail`, `park`, a profile on a command step) and the prompt budget are the Worker's own policy: they stay in the Worker package and run after the validator.
- **Failure: adopt.** A step that fails after its retries skips the steps that depend on it; independent steps still run. The run is `failed` if any step failed.
- **Retries: adapt.** `retries` adds attempts after a certain failure: a recorded nonzero exit with the process group gone. Uncertainty never retries (ADR-0005). A timeout is not retried: the run expiry is shared by all steps and retries, set at preparation from the job's `timeout_seconds` or the default and frozen. A retried prompt step is a new attempt with a new directory and session, and its prompt says it is attempt N after a failure and asks the agent to check the checkout for partial work first (herdr-kata's wording for a resumed limit hold).
- **Prompt steps: adapt.** herdr-kata shares one agent, and its context, across a run's prompt steps unless `agent_mode: "fresh"` or secrets force a fresh one. Each omp run here is a process, so every prompt step is fresh and steps hand off through the checkout and the run's Issue comments. herdr-kata's `{{input}}` and `{{previous}}` placeholders, `--note` and `$HERDR_KATA_PREVIOUS` are rejected: kata's workflow format defines no substitution, the spec has no run input, and a note is a one-line side channel that exists only because herdr-kata's agents report through a CLI. A prompt containing a literal `{{input}}` is sent as written. `about` and the workflow name go into the prompt (ADR-0009).
- **Per-step profile: adapt.** A prompt step may name a profile in `options.profile`, as the job does. The profile is only a command line, so there is no fresh-agent or cap interaction. A command step or the workflow with a differing profile is unsupported, as in herdr-kata.
- **Command steps: adopt.** `sh -c <command>` in the checkout, in its own process group, as the worker's user. Status, start and end times, and group id are saved in a receipt (and, immediately after start, a start record) before anything else reads it. Output is drained continuously to `output.log`, keeping the first 1 MiB and last 256 KiB with a marker between. Exit 0 succeeds only with a certain receipt and an empty group. A missing receipt, an interruption or a surviving descendant is `unknown` and holds (ADR-0005). The environment drops the worker's kata credentials and routing selectors, adds the job's secrets, then `TERN_KATA_RUN`, `TERN_KATA_RUN_DIR` and `KATA_PROJECT`. A descendant that calls `setsid` and detaches can escape the group; herdr-kata documents the same limit.
- **Output capture: one best-effort rule.** The agent's stdout and stderr files and a command step's `output.log` are recorded the same way: a capture that cannot be opened or written is dropped from that point on, the process carries on and the Run or step settles from what the process did, and the loss is saved with the attempt's exit record and its reason. A command whose log cannot be written is not held (it was once `execution_error`): its output is a record, not part of its result, and it settles from its exit status with no output tail in the summary. The loss rides into a workflow step's record, a resumed attempt starts without it, and `worker status`, the run detail and the Worker's log (once) say "output not recorded: <reason>". The agent capture keeps its first-bytes cap and per-line parser feed and the command capture its head-plus-tail shape; only the error rule is shared.
- **Cancellation: adopt.** At the run expiry or an `A` on a running run the group gets SIGTERM, then SIGKILL after 10 s.
- **Prompt cap: adapt.** herdr-kata caps prompt attempts per generation (`max_run_prompts`, default 12, 1 to 100) and checks the sum of `1 + retries` over prompt steps, plus loop visits, at admission and again when re-read; a runtime `prompt_budget` hold exists for loops. Without loops the worst case is fixed by the definition, so only the static check is kept: a definition over the cap is unsupported with `prompt_budget <count> > <cap>`. A resume grants a fresh count.
- **Maker/checker loops (`options.on_fail`): reject.** They add a backward edge, saved verdicts, a finding comment chain, typed replies, notes, four hold reasons and a resume target per reason, and the spec has no story for them. The spec left the door open "unless the design review adopts them"; this review does not. A workflow that declares `on_fail` is shown as unsupported with that reason and does not run, so no checker step silently runs once as an ordinary step.
- **Park on failure (`options.on_failure: "park"`): reject.** It holds a failed step for a resume. The spec's resume covers uncertainty only, and a failed run records `failed` with its summary and comments the Issue. The key is shown as unsupported with a reason, not ignored, because ignoring it changes what the author asked for.
- **Other unknown option keys: adopt herdr-kata's rule.** Unknown keys warn and are ignored.
- **The Workflow card tells, and never blocks.** The card saves any Workflow kata accepts, including one this machine's Worker refuses by the decisions above, because the Workflow may be meant for another machine's Worker. Under the text it says what this machine's Worker would refuse and why, from the Worker's own check (the one its planning and `worker status` use) and the prompt budget of this machine's `worker.toml`; the Workflows Page inspector says the same of the stored Workflow. When `worker.toml` cannot be read the note says the budget was not checked.

## Consequences

- A workflow author who relied on herdr-kata's shared agent context must put what steps need in the checkout or the Issue.
- Steps are serial; independent steps do not run in parallel.
- Graceful shutdown during a step kills its group and holds the run `interrupted`; resume continues an omp step as a new headless run with `--resume` and a continuation prompt (ADR-0005), and a command step reruns.
